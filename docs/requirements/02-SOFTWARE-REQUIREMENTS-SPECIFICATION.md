# LocalCam Software Requirements Specification

Status: Current implementation baseline

## Functional requirements

| ID | Requirement | Priority | Status | Verification |
|---|---|---|---|---|
| FR-001 | The application shall start as a single-window WPF desktop app and show its dashboard shell before nonessential video-engine initialization completes. | Must | Implemented | FAST-BUILD and cold-start launch check |
| FR-002 | The application shall load persisted settings from `%LocalAppData%\\LocalCam\\settings.json`, recover from the previous valid backup when the primary file is malformed, and serialize saves atomically. | Must | Implemented | `SettingsStoreTests` normalization, backup recovery, concurrent-save, and invalid-file tests |
| FR-003 | The application shall restore persisted window bounds when valid and persist the latest normal bounds during window movement, resizing, state changes, and close; restore shall apply the saved size without additional application-level clamping. | Should | Implemented | Manual UI check: move/resize, maximize/restore, close/reopen, below-minimum saved-size behavior, and multi-monitor visibility |
| FR-004 | Each discovery process shall run the persisted `LastSuccessfulDetectionMethod` first when it is a valid local method, then continue through the remaining local methods. With no valid preferred method, Tapo UDP broadcast and ONVIF WS-Discovery hint collection shall run concurrently; with a preferred method outside that pair, the preferred method shall finish first and the pair shall run concurrently next; when the preferred method is in the pair, it shall run first and the other member follows. The remaining default local order shall be mDNS/DNS-SD, SSDP/UPnP, ARP-seeded probing, RTSP OPTIONS probing, then subnet fallback. A successful scan shall persist its successful local method at runtime for the next discovery process. After local methods finish, the app shall automatically run the existing adaptive unicast search whether or not local cameras were found. It shall select up to eight additional private /24 networks in at most two stages from recent confirmed camera addresses, adapter DNS/DHCP clues, and bounded common home-network candidates, use available route/gateway clues, and inventory at most 2,032 additional hosts through existing cancellable unicast validation and per-scan host cache. When untried candidates remain within the global limits, the second stage shall run even if the first stage found cameras, and detections/evidence from both stages shall be merged. Local detections shall be published and may begin playback while the adaptive search continues. The adaptive verifier shall prioritize responsive candidates with confirmed open RTSP ports, then use remaining endpoint budget to check other responsive candidates on ports 554 and 8554. Across both stages, it may issue at most three unauthenticated RTSP requests per endpoint, capped at 64 endpoints; it shall validate the RTSP status line and matching CSeq and recognize authentication challenges as service evidence. It shall validate ONVIF WS-Discovery matches, SSDP response headers and bounded UPnP descriptions, camera-related DNS-SD service records, and RTSP replies; merge evidence by host; and avoid repeating the general host inventory. Link-local multicast is not represented as crossing routers. Discovery shall not send saved RTSP credentials. | Must | Partial | Priority-order and concurrent-hint checks, planner/parser/probe and staged-budget checks, FAST-BUILD, and controlled VMware NAT/routed-network verification; real multi-vendor camera coverage remains pending |
| FR-005 | The application shall expose retryable discovery and status feedback. | Must | Implemented | UI acceptance check |
| FR-006 | The application shall display one camera tile per unique camera identity, using MAC address when known and IP address otherwise. Detection refresh shall preserve existing camera-to-tile associations when result order changes. | Must | Implemented | Reconciliation tests and UI acceptance check |
| FR-007 | The application shall build RTSP URLs from credentials, detected host, and normalized stream path. Port `554` is the default; port `8554` may be selected only after an RTSP OPTIONS response is validated on that endpoint. The confirmed port shall persist in the recent-connection cache and be used on reconnect. | Must | Partial | URL-port selection and cache persistence tests, FAST-BUILD, and live RTSP checks on ports 554 and 8554 |
| FR-008 | Saving Settings shall not require RTSP credentials; empty username and/or password values may be persisted. Starting playback with invalid or missing RTSP configuration shall open Settings and show `RTSP credentials are missing or invalid.`, highlight only the missing credential fields, and focus the username field. When discovery finds a camera while the shared RTSP configuration is incomplete, discovery shall stop and open Settings. A credential rejection from a camera during discovery-triggered auto-play shall remain a per-card playback error and shall not open Settings or stop discovery. Credential-related failures from user-requested playback shall continue to open Settings. | Must | Implemented | Settings save and stream-start UI acceptance checks; incremental discovery credential checks |
| FR-009 | The application shall support per-camera Play/Stop and global Play all/Stop All actions. A stream becomes live only after LibVLC confirms playback; this transport/play state is distinct from video-output confirmation. Health monitoring shall allow video-output initialization grace, record the first video-output or decoded/displayed-frame evidence, report a distinct per-camera error if video evidence does not arrive before the existing stale deadline, require consecutive unhealthy samples before stale recovery, and use bounded per-camera recovery with cooldown. Unexpected terminal playback events receive one bounded restart attempt. A playback failure shall remain isolated to its camera card so other active cameras continue streaming and remain visible with their video surfaces attached during recovery discovery; the card shall show a concise classified error when available. Discovery-triggered playback shall start as soon as each new camera is reported, without waiting for discovery completion, and a failed camera shall not block starts for other cameras. On system suspend or hibernate, the application shall invoke Stop All and retain detected tiles and connection state; system resume shall not auto-start playback. | Must | Partial | Automated reconciliation and stream-health tests, FAST-BUILD, and pending live multi-camera/no-video verification |
| FR-010 | The application shall clean up stream and LibVLC resources on stop and close. | Must | Implemented | Lifecycle test/manual check |
| FR-011 | The application shall capture snapshots only from active streams and use unique filenames. | Must | Implemented | Snapshot test |
| FR-012 | The application shall support one manual recording session across all cards and stop it through the normal Stop All path before system suspend or hibernation. | Must | Implemented | Recording state tests and power-transition UI check |
| FR-013 | Starting recording on another card shall stop the current recording before switching. | Must | Implemented | Recording integration test |
| FR-014 | Recordings shall use `.ts` output and roll over at 60 minutes while playback remains active. | Must | Implemented | Timer/recorder test |
| FR-015 | Recorder stop, end, or error shall clear recording UI state and report activity. | Must | Implemented | Failure-path test |
| FR-016 | Settings shall support RTSP credentials, stream path, reconnect recent cameras on startup, snapshot folder, recording folder, and a link to the camera setup guide. When recent connections exist, startup reconnect and Detect and Play shall request playback for cached cameras immediately and also run local discovery to find cameras missing from the cache. Discovery shall start each newly reported identity while the scan continues, preserving existing active streams and camera-to-tile identity. Incomplete shared RTSP settings stop discovery and open Settings after a camera is found; camera-specific playback rejection with credentials present remains visible on that camera card while discovery continues. | Must | Partial | Settings UI, camera setup guide link, cache-plus-discovery timing, missing-settings cancellation, credential distinction, and recovery acceptance checks |
| FR-017 | The application shall persist selected non-default save folders and use default Pictures/Videos LocalCam folders when unset. | Must | Implemented | Persistence test |
| FR-018 | The application shall write structured diagnostics for startup, discovery, settings, streaming, snapshots, recording, entitlement, and purchase through one logging route shared by Debug, Release, and installed builds. Logs shall remain in application data, never beside the launched executable; packaged application data shall be removable with the package. Diagnostics shall redact credentials, complete RTSP URLs, and other secret-bearing values, rate-limit repeated LibVLC runtime messages, and delete log files older than seven days. | Should | Partial | Redaction, retention, and schema tests; packaged/unpackaged path and uninstall verification pending |
| FR-019 | Packaged Store releases shall use the Microsoft Store MSIX delivery path for app updates; LocalCam shall not expose an in-app update checker, installer, queue-recovery flow, or update UI. Store release packages shall use the manifest Identity version, retain a fourth component of `0`, and increment the Build component by one from the highest relevant Partner Center version unless an approved release decision specifies otherwise. | Should | Implemented/packaged-only | Store submission guide, x64 package validation, manifest/version evidence, and Store-flight delivery check |
| FR-020 | The application shall provide persistent System, Light, and Dark theme preferences, apply the selected WPF theme before the first window visual tree is initialized, refresh LocalCam brush instances after a preference change, and use Windows-provided Fluent theme resources for light/dark surface distinction and accent text. | Should | Partial | Settings persistence, startup-order, brush-refresh, native-title-bar UI check, and host-theme visual check; automated theme coverage remains |
| FR-021 | MainWindow and SettingsWindow shall use native Windows/WPF window frames without decorative outer client-border wrappers; Settings shall use the default WPF behavior for its theme selector and dropdown. | Should | Implemented | XAML inspection, FAST-BUILD, and manual native-frame/System-Light-Dark Theme ComboBox check |
| FR-022 | The application shall retain recent confirmed camera connections locally for seven days and reconnect them before/while refreshing discovery on startup or Detect and Play. Cached streams shall begin playback without waiting for discovery; discovery shall still run after successful reconnects to find uncached cameras. A cache entry shall be evicted after two consecutive reconnect failures. Cache confirmation shall be bound to the originating camera/playback attempt and never to a reordered tile. Detect and Play shall submit each detected stream start once per route. | Must | Partial | Cache-policy tests; controlled check with fewer cached than reachable cameras, discovery/cached-playback overlap, timeout/failure accounting, and identity deduplication |
| FR-023 | The application shall replace auto-detect and auto-stream preferences with a Reconnect recent cameras on startup preference, and invalidate the recent-connection cache when shared RTSP credentials or stream path change. | Must | Implemented | Settings persistence and invalidation tests |
| FR-024 | The application shall initialize the video engine after the first dashboard render, show preparation or failure status, provide retry for initialization failure, and prevent stream actions until the engine is ready. A repeated launch shall activate the existing single instance. | Must | Implemented | Cold-start UI check, failure/retry check, readiness-gating check, and repeated-launch activation check |
| FR-025 | Each detected camera card shall provide an icon-only Information action that opens a compact, non-resizable modal with available camera identity, discovery, RTSP connection, playback, and recording details. The dialog shall identify unavailable per-camera discovery metadata as unavailable, provide a Copy action for all displayed information, and shall never display or copy RTSP credential values or a credential-bearing URL. | Should | Implemented/verification pending | Information view acceptance check, including missing data, clipboard output/failure, credential privacy, accessibility, theme, and in-video overlay behavior |

## Non-functional requirements

| ID | Requirement | Priority | Status | Verification |
|---|---|---|---|---|
| NFR-001 | The supported runtime and package architecture shall remain x64-only. | Must | Implemented | Project/package inspection |
| NFR-002 | Discovery shall use bounded concurrency, protocol receive windows, response sizes, request limits, host/range limits, and timeouts so a scan remains cancellable and remote responses cannot cause unbounded parsing or body reads. The automatic additional pass shall cap its candidate ranges at 16, expanded ranges at eight /24 networks across two stages, total inventory at 2,032 hosts, confirmed-open and responsive-host fallback RTSP checks combined at 64 endpoints across both stages, and each RTSP response at 16 KiB. | Must | Partial | Parser and adaptive-planner/probe tests, code review, and controlled-network duration/cancellation check |
| NFR-003 | User-facing discovery text shall remain brand-neutral. | Must | Implemented | Text audit |
| NFR-004 | User-visible controls shall follow the documented visibility, enablement, and keyboard-accessibility rules. | Must | Implemented | UI acceptance matrix |
| NFR-005 | Video overlays shall be hosted inside the VideoView content and remain attached during resize and active playback. | Must | Implemented/needs regression evidence | Live UI check |
| NFR-006 | Failures in critical workflows shall be visible to users and not silently swallowed. | Must | Partial | Per-card playback errors and recovery-exhaustion path implemented; live failure-path verification pending |
| NFR-007 | Settings and diagnostics shall remain local to the device unless future scope explicitly adds remote services. | Must | Implemented | Code/dependency review |
| NFR-008 | Critical behaviors shall have automated tests or a documented manual verification path. | Must | Partial | Discovery parser, adaptive-planner, adaptive RTSP request-selection, and legacy-settings migration tests added; controlled routed-network, authentication-challenge, and port-8554 verification remains pending, as do live multi-camera and graphics-path checks |
| NFR-009 | Repository builds, tests, packaging, and generated artifacts shall use the exact .NET SDK version pinned in `global.json`; the current pinned version is `10.0.400` with roll-forward disabled. | Must | Implemented | `global.json` inspection, `dotnet --version`, and Visual Studio 2026 FAST-BUILD |

## Constraints and non-goals

See [05 Decisions and Constraints](05-DECISIONS-AND-CONSTRAINTS.md). Requirements for manual camera entry, arbitrary RTSP URLs/ports, universal camera support, and architecture generalization are not current requirements.
